01 · Architecture at a glance

Four layers, shared contracts

Ximo is organized as a pnpm workspace: the mobile client and admin console call a central API, while shared libraries provide database schemas, generated validation, and typed API utilities.

User experience

Mobile application

Native-first app with web support, route-based navigation, Clerk authentication, server-state queries, local persistence, localization, and media/device integrations.

Operations

Admin console

React single-page app with Clerk login, server-verified admin access, moderation, users, events, badges, notifications, profile effects, and settings.

Business logic

API server

Express API is the control point for account checks, content and social operations, rewards, moderation, upload handling, media composition, AI and push integrations.

Shared foundation

Workspace libraries

Database package, OpenAPI specification, generated Zod schemas, React Query client, and server-side AI integration packages live alongside artifacts.

Core pattern: the client renders and caches the experience; authenticated API routes enforce identity and application rules; PostgreSQL stores structured state; object storage holds media. Some local cache and retry patterns improve resilience but do not constitute a full offline mode.

Data path examples

Read: Ximo obtains a Clerk session → API validates the session and user scope → Drizzle queries PostgreSQL → client updates query/context state.

Media: app uploads image/video → server checks limits and media properties → GCS stores assets → API returns a media reference used by content features.

Real time: authenticated SSE streams carry selected events; client reconnect logic and polling support foreground refresh. Current event fanout is process-local.

Developer quality tools

  • Monorepo manager: pnpm 10.26.1 with shared dependency catalog and committed lockfile.
  • Type system: TypeScript ~5.9.2; root scripts typecheck shared libraries and artifact packages.
  • Lint / format: ESLint 10.x and Prettier 3.x.
  • Tests: Vitest 4.x; API tests use Supertest where appropriate.
  • Build: Expo/EAS for mobile; Vite for admin; esbuild for API packaging.

Build configuration

  • EAS profiles include internal Android APK and production Android App Bundle / iOS device builds.
  • Build profiles declare Node 22 and pnpm 10.26.1 for mobile builds.
  • Expo OTA updates are disabled, so app-level fixes require a new native build / distribution cycle.
  • Only Android EAS workflow files were found in GitHub Actions; workflows are manually triggered.

Operational characteristics to know

API is a single Express service backed by PostgreSQL and GCS. Current SSE fanout and several throttles/counters are process-local; choose a single-instance limit or add shared coordination before horizontal scaling. Startup migrations run after the server opens its port. Health response is process-level and does not establish database or provider readiness.

Contract / privacy note: shared generated API contracts cover only part of the route surface. Public media endpoints and intended-private journal/gallery data should be checked together against the storage visibility policy. These are implementation notes, not claims that a production incident has occurred.
